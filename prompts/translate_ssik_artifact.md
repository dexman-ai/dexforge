### **2. The `ssik_core` Boundary (CRITICAL)**

**DO NOT REIMPLEMENT COMPLEX NUMERICAL KERNELS.** The heavy mathematical lifting has already been extracted into hand-maintained Rust libraries (`src/math/ssik_core.rs`, `kinematics.rs`, and `postprocess.rs`).

* Your job is to extract the **arm-specific constants** and **straight-line algebraic blocks** from the Python file, and wire them up to these static core functions.
* **Kernel Mapping:** Wherever the Python artifact imports and calls `_sp6_runtime.solve`, `eliminate_q0_q1`, `lm_refine`, or root-finding matrices, you must map these directly to the equivalent `ssik_core` or `kinematics` functions (e.g., `ssik_core::sp6_solve`, `ssik_core::rr_real_roots`, `kinematics::lm_refine6`).
* **The Möbius / `pinv` Fallback:** If the Python artifact utilizes a randomized Möbius transform or `pinv` fallback for ill-conditioned generalized eigenproblems, **do not transpile it**. Instead, follow the established DexZero template: solve a deterministically perturbed pose (e.g., offset by $0.1\text{mm}$) using `rr_real_roots`, and snap it back to the target pose using `lm_refine6`.

### **3. Compilation & Type Constraints**

1. **Strict `#![no_std]` Compatibility:** The code must not link to the standard library (`std`). It must be completely free of heap allocations (no `Vec`, `Box`, `BTreeMap`).
2. **`nalgebra` Typing:** Map all incoming matrix/vector types to fixed-size static types.
* 3D vectors $\rightarrow$ `nalgebra::SVector<f64, 3>` or `[f64; 3]`.
* $4\times4$ transformation matrices $\rightarrow$ `nalgebra::SMatrix<f64, 4, 4>`.


3. **Fixed-Size Accumulation:** Map the final output configurations to a fixed-size stack array containing optional variants: `[Option<[f64; DOF]>; MAX_SOLUTIONS]`.
4. **Deterministic Math:** There must be zero unbounded loops. Every numeric approximation must have a hardcoded `for _ in 0..MAX_ITER` ceiling.

### **4. Translation Execution Steps**

**Step 1: Extract Constants**
Extract all hardcoded spatial dimensions, link lengths, joint limits, and baseline offsets from the Python script. Emit them as Rust `const` arrays (e.g., `[[f64;4];4]`, axes, limits, `DOF`, `T_HOME`). Do not "simplify" the geometry or zero out floating-point noise. Format all float literals explicitly (e.g., `2.0_f64`).

**Step 2: Lower the Algebraic Block**
Transpile the straight-line scalar arithmetic blocks (the `th14_x*`, `q6_x*`, `dinr_*`, SP3 boundary branches, etc.).

* Map `math.sin(x)` $\rightarrow$ `x.sin()`, `math.atan2(y,x)` $\rightarrow$ `y.atan2(x)`.
* Preserve the exact variable assignment ordering to prevent floating-point accumulation drift between Python and Rust.

**Step 3: Define the Driver Interface**
Generate a Rust interface that matches the existing DexZero driver signatures (based on the template you chose in Step 1).

* Example: `pub fn solve(&T, max_solutions, q_seed, respect_limits, allow_refinement, policy, refinement_max_iters) -> [Option<[f64; DOF]>; 16]`.

**Step 4: Branch and Boundary Conditions Validation**
Ensure that operations that could result in `NaN` (e.g., `acos` or `asin` receiving an argument outside $[-1.0, 1.0]$) catch the domain error explicitly and `continue` to the next potential solution root rather than panicking.
